# Design

## Context

`dbrel`'s current frontend is a Django app (`src/dbrel/web/`) with four server-rendered pages
(`search.html`, `station.html`, `train.html`, `line.html`) built on Django Template Language,
backed by SQLAlchemy queries in `queries.py` (shared with the CLI). Every rendered page has a
JSON mirror already (`/api/suggest`, `/api/station/<id>/board`, `/api/train/<id>/route`,
`/api/line/<id>/directions`, `/api/line/<id>/stations`, `/api/line/<id>/around`) — a full JSON
API layer already exists, it's just currently only consumed by that same Django page's inline
JS (`browse.js`). The `dep_pred`/`pred` fields these responses carry are wired through every
template already but hardcoded `None` — the shape for a predicted-delay figure exists, nothing
populates it.

`bahn-buddy-predict` is a separate, untracked directory: a React 19 + TanStack Start (Vite,
Bun, TypeScript strict) app generated by Lovable, styled with Tailwind v4 + shadcn/ui (`ink`/
`panel`/`teal` palette, dark-mode default, DE/EN toggle). It has exactly one route today
(`/`), toggling between two components — `TrainSearch` and `TrainOverview` — entirely against
hardcoded mock data in `src/lib/trains.ts` (4 sample trains, a deterministic fake per-stop delay
cycle, a fabricated reverse-direction leg, a synthetic 120-minute headway). `@tanstack/
react-query` is provisioned but has zero query hooks defined anywhere — it's the natural seam
for real API calls. The template's default build targets Cloudflare via `nitro`, which doesn't
match `dbrel`'s actual (self-hosted, single Django process) deployment.

`stop_delay_average` (from the already-archived `add-holiday-aware-stop-averages` change) is the
only source of "expected delay" data in this system — `dbrel` has no live prediction model; the
prior LightGBM pipeline was deliberately removed and its replacement is a separate, not-yet-
scoped future effort (see `dbrel-ml-pipeline` memory). This change does not touch that decision.

## Goals / Non-Goals

**Goals:**
- Make `bahn-buddy-predict` the only `dbrel` frontend, with feature parity (search, train route,
  station board, line detail) against the four things the Django UI covers today.
- Every value the frontend displays is real, sourced from the existing JSON API (extended where
  needed), including the fields the template shows that the current Django UI doesn't (e.g. a
  named "expected" time per stop, direction picking, platform).
- Delete all mock data and mock-driven logic from the template; nothing fabricated ships.
- Preserve the template's own visual language for the two views it has no precedent for
  (station board, line detail) rather than inventing a new style.

**Non-Goals:**
- No live/per-trip delay prediction. "Expected" times are the `stop_delay_average` historical
  mean only — this was decided explicitly (see proposal), not deferred.
- No new backend data model or aggregation logic. `stop_delay_average`, `queries.py`'s existing
  query functions, and the models they read are used as-is; only their JSON exposure changes.
- No parallel-running fallback to the Django-rendered pages. This is a full replacement, not a
  staged rollout behind a flag.
- No authentication, multi-tenancy, or write paths — the frontend remains read-only, matching
  today's UI.
- No automated test suite is introduced for the frontend in this change (none exists in the
  template today, and adding one is a separate concern from wiring it to real data).

## Decisions

**1. Extend `queries.py` to populate `dep_pred`/`pred` from `stop_delay_average`, in place of
the current hardcoded `None`.**
The response shape (`p50_min`/`lo_min`/`hi_min`) already exists in every relevant query
function; since there's no live model, `p50_min` becomes the average's mean delay in minutes and
`lo_min`/`hi_min` are dropped (or both set equal to `p50_min`) rather than fabricating an
interval `stop_delay_average` doesn't have. Alternative considered: return only a single
`expected_delay_min` field and drop the interval shape entirely — rejected because the JSON
shape is otherwise unchanged for every other consumer of these functions (the CLI, if anything
depends on it) and keeping the field names stable is simpler than a wire-format resurvey.

**2. Keep `queries.py`/`views.py` as the single backend surface; extend it, don't fork a second
API.**
The frontend calls the existing JSON endpoints, extended with whatever fields it needs that
aren't there yet (`platform_code`, `n_stops`/`n_stops_tracked`, origin/destination names,
replacement-bus flag, cancellation state). Alternative considered: a separate REST/GraphQL layer
purpose-built for the frontend — rejected as unnecessary duplication; `queries.py` already
returns structured dicts assembled from the same SQLAlchemy models the CLI and Django templates
use, and the Django templates are being deleted in this same change, so there's no compatibility
constraint holding the JSON shape back from evolving.

**3. Move from the template's single toggle-state page to real TanStack Router file-based
routes:** `/`, `/station/$stationId`, `/train/$trainId`, `/line/$lineId`.
This restores the shareable/bookmarkable URLs the Django UI already has
(`/station/<id>/`, `/train/<id>/`, `/line/<id>/`) and gives the two new views (station board,
line detail) a natural home instead of overloading the existing search/overview toggle state.
Each route fetches its own data via a `useQuery` hook against the matching API endpoint.

**4. Delete the mock data module and every function built only to serve it.**
`src/lib/trains.ts` (the `TRAIN_SERVICES` array, `getStopDelay`, `getTrainDirections`,
`searchTrains`, `getTrainService`) is removed outright rather than kept behind a flag or as a
fallback. `TrainSearch.tsx` and `TrainOverview.tsx` are rewritten against `react-query` hooks
calling the real endpoints. `src/lib/prediction.ts`'s `addMinutes()` helper is generic time math
and may be kept if still useful for formatting API-returned delay minutes into clock times.

**5. Build the two new views (station board, line detail) as new components using the
template's existing shadcn primitives and palette tokens, not a new design system.**
Reuse `src/components/ui/*` (card, table, badge, etc.), the `ink`/`panel`/`line`/`fog`/`teal`
semantic tokens from `styles.css`, the same 3-tier delay color rule (teal `<6`, amber `6–14`,
danger `≥15`), and the existing DE/EN `copy` dictionary in `src/lib/i18n.ts` (extended with new
keys for these views' labels). Alternative considered: hand-roll new styling for these two views
since no template precedent exists — rejected, since the goal is one coherent app, not a bolted-
on section that looks different from the rest.

**6. Revised during implementation — run the built TanStack Start server (`nitro`, `node`
preset) as its own small persistent process, reverse-proxied alongside Django, instead of a
pure static build.**
The original plan was a pure static build served by Django (see the superseded paragraph
below), avoiding a second runtime entirely. Implementation found that doesn't hold up: TanStack
Start's own static-shell mechanism for this (`tanstackStart.spa.enabled`, which prerenders one
static HTML shell by crawling the app with a built-in dev-preview server) throws
(`server.fetch is not a function`) in this project's pinned toolchain version
(`@tanstack/react-start` 1.168.32 / `@lovable.dev/vite-tanstack-config` 2.23.1) — confirmed to be
in the built-in crawler itself, not in this project's code: the failure reproduces identically
with and without the app's own custom `src/server.ts` server-entry wrapper. The underlying build
is otherwise unaffected — `nitro: { preset: "node" }` (in place of the default `cloudflare`
preset) produces a working `.output/server/index.mjs` alongside `.output/public/`; run directly
(`node .output/server/index.mjs`), it renders the app's real HTML correctly on every request.
So: run that file as a small always-on Node process. **Further correction**: there is no
existing reverse proxy to extend — per the project's own README, `dbrel` is a single local
command (`uv run dbrel serve`, Django's own `runserver` on one port; confirmed by reading
`cli.py`'s `serve` command directly, not assumed). Introducing a real reverse proxy (nginx,
Caddy, ...) as a new piece of infrastructure for what is a local single-operator tool would
contradict the project's own "one command, one port" ethos. Instead: `dbrel serve` spawns the
built Node server itself as a subprocess (fixed local port, e.g. `127.0.0.1:<port+1>`) alongside
Django, and Django's own `urls.py` gets one more route — a catch-all placed after every real
`/api/*` pattern — whose view proxies the request (via `httpx`, already a dependency) to that
Node process and streams the response back. The result is still one command and one port for
the operator; the two processes are an internal implementation detail of `dbrel serve`, not
something the operator manages separately. `nitro`'s Cloudflare/edge-worker default is still
dropped (that part of decision 6 stands); only the "no second process" property is given up, and
that second process is fully owned and supervised by `dbrel serve` itself (started with it,
killed when it exits), not a separately-administered systemd unit. Alternatives considered:
- *Capture one static HTML shell manually* (spin up the built server briefly during the build,
  fetch `/`, save it as `.output/public/index.html`, kill the server — replicating what the
  broken built-in crawler was trying to do) — rejected: the captured shell is only exactly right
  for `/`; every other route relies on the client hydrating over a server-rendered DOM built for
  a different route, which risks a hydration mismatch on first paint (React recovers by
  re-rendering client-side, so it would likely still work, but this was verified only for the
  happy path, not case-by-case).
- *Keep investigating the toolchain bug* (try other package/version combinations, or wait for
  an upstream fix) — rejected: unbounded effort for an already-beta feature, with the persistent-
  process alternative available now and well-understood.

*(Superseded — kept for context) Original plan: serve the built frontend as static assets from
the existing Django process, dropping the template's Cloudflare/`nitro` build target.* `vite
build` would produce a static bundle; Django would serve it (e.g. via its existing static-file
serving, or a catch-all view for the SPA's routes) behind the same reverse proxy `dbrel` already
runs behind — no second runtime needed, since this is a client-rendered SPA fetching JSON, not a
server-rendered app. Superseded by the toolchain finding above.

## Risks / Trade-offs

- **[Risk]** Two brand-new views (station board, line detail) with no template precedent could
  drift stylistically from the rest of the app. → **Mitigation**: decision 5 — reuse existing
  primitives/tokens/copy patterns exclusively; no new component library or ad hoc CSS.
- **[Risk]** `stop_delay_average` has zero samples for many real combinations (new stations,
  rare services, the known S9/S46 replacement-bus skew already accepted as closed per
  `dbrel-aggregates` memory). A UI that silently shows "0 min" or omits the field would misrepres
  ent "no data" as "on time". → **Mitigation**: the `web-frontend` spec's "No average exists for
  the stop" requirement makes an explicit empty state mandatory, not optional polish.
- **[Risk]** Dropping the Cloudflare edge-worker path loses the current Django UI's "works with
  JavaScript off, no loading flash" property for the station board specifically (called out in
  `views.py`'s own docstring as a deliberate property of today's implementation). → **Mitigation
  **: accepted as a conscious trade-off — this is an internal reliability-monitoring tool, not a
  public-facing page needing no-JS support; not treated as a regression to silently avoid
  mentioning.
- **[Risk]** Revised decision 6 means `dbrel serve` now runs two processes (Django, the
  TanStack Start Node server) instead of one. → **Mitigation**: `dbrel serve` spawns and owns
  the Node process itself (subprocess, killed on exit) — the operator still runs one command on
  one port, matching the project's existing "one command" ethos; no new externally-administered
  infrastructure (proxy, systemd unit) is introduced.
- **[Risk]** The Django catch-all proxy view adds a new failure mode (Node process not yet up,
  crashed, or slow) that didn't exist when Django rendered pages itself. → **Mitigation**: the
  proxy view returns a clear 502 with a short explanatory body when the Node process is
  unreachable, rather than hanging or a bare Django 500 page.
- **[Risk]** Extending `queries.py`'s JSON shape (new fields, changed `dep_pred`/`pred`
  semantics) has no other consumer to break once the Django templates are deleted in this same
  change — but if that deletion and the frontend rollout aren't sequenced together, there's a
  window where the shape changes under the old templates' feet. → **Mitigation**: covered in the
  migration plan below — extend the API first, delete Django pages only once the new frontend
  already covers their functionality.
- **[Risk]** The build toolchain (Node, Vite, TanStack) is new to what has otherwise been a
  Python-only project, and per revised decision 6 now also runs at deploy time (the built Node
  server), not just at build time. → **Mitigation**: a single `node .output/server/index.mjs`
  process with no other runtime dependency (no Bun required — `npm`/`node` alone build and run
  it); spawned and supervised by `dbrel serve` itself, not a separate operational concern.

## Migration Plan

1. Extend `queries.py` (and `views.py`/`urls.py` where a JSON endpoint is missing, e.g. a full
   line-detail JSON shape matching `line_detail()`) to populate `dep_pred`/`pred` from
   `stop_delay_average` and to carry every field the frontend needs.
2. In `bahn-buddy-predict`, delete `src/lib/trains.ts` and its mock-only call sites; add
   `react-query` hooks against the real endpoints; rewrite `TrainSearch`/`TrainOverview` to use
   them.
3. Add the station-board and line-detail routes/components, and wire real TanStack Router
   file-based routes (`/station/$stationId`, `/train/$trainId`, `/line/$lineId`) in place of the
   single toggle-state page.
4. Build the frontend (`vite build`, `nitro: { preset: "node" }`). Extend `dbrel serve` (`cli.py`)
   to spawn `.output/server/index.mjs` as a subprocess on a fixed local port alongside Django, and
   add a catch-all view in `urls.py` (after every `/api/*` pattern) that proxies any other request
   to it via `httpx`; confirm every view renders against the live `dbrel.sqlite` database with
   real stations/lines, through the single `dbrel serve` port.
5. Remove the Django-rendered pages and their view functions
   (`views.index`/`station`/`train`/`line`, the four templates, `app.css`/`app.js`/`browse.js`)
   once the new frontend has been verified to cover their functionality.
6. Manual verification pass (no automated frontend test suite exists) against the running
   instance: search, a train route with a tracked and an untracked stop, a station board for a
   tracked and an untracked station, and a line detail page for a normal line and a known
   replacement-bus line (S9/S46).
